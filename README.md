# vk-bench

在**任意支持 Vulkan 的 GPU** 上测四件事，并给出架构画像：

1. **向量/ALU 算力** —— fp32 / fp16 / fp64 / int32 / int8(DP4A) / SFU / 位运算 / 子组运算 / 共享内存带宽
2. **矩阵单元** —— `cooperative matrix` 各配置的实测 TFLOPS/TOPS（有独立矩阵硬件还是靠 ALU 模拟，一眼看出）
3. **缓存容量与延迟** —— 指针追逐的延迟-容量曲线，按容量台阶推断 L1/L2/末级缓存/显存四级的拐点
4. **带宽** —— 读/写/拷贝随工作集大小的曲线（显存带宽与各级缓存平台），外加访问步长扫描与 DMA 拷贝引擎对照

目标版本范围 **Vulkan 1.1 ~ 1.4**：instance 以 1.1 基线创建，按设备 `apiVersion` 逐级探测并启用 1.2/1.3/1.4 特性；纯 1.1 设备上基础测试照跑，矩阵等高级项按扩展可用性自动降级并如实标注。

产物是**一个自包含 exe**：运行时动态加载 `vulkan-1.dll`（不链接 import lib、不依赖 Vulkan SDK），无窗口、无 swapchain，纯计算队列——独显、核显、无视频输出的计算卡都能跑。

## 构建

需要：Visual Studio 的 C++ 工具链、Node.js（生成脚本用）、以及两个只在**编译期**需要的依赖：glslang（GLSL→SPIR-V）和 Khronos Vulkan-Headers。

```bat
:: 1. 拉编译期依赖（直连 GitHub release / codeload，带续传）
powershell -ExecutionPolicy Bypass -File tools\fetch_toolchain.ps1

:: 2. 编译（编 shader → 内嵌 SPIR-V → 生成报告模板… → cl）
build.bat
```

产物 `vkbench.exe` 可直接拷到别的机器（目标机只需要装了显卡驱动，不需要装 Vulkan 运行库以外的东西）。

## 运行

```bat
vkbench.exe                     :: 交互菜单（先列设备，再选测试档位）
vkbench.exe                     :: 交互菜单（选 1 或直接回车 = 完整档）
vkbench.exe --full              :: 完整档（默认，约 1.5-3 分钟：ALU 7 次重复、缓存 5 次、1 KiB→1 GiB 全扫）
vkbench.exe --quick             :: 快速档（采样减半，约 40 秒，扫频取偶数幂次）
vkbench.exe --caps              :: 只探测能力，不测试
vkbench.exe --list              :: 只列支持 Vulkan 的计算设备
vkbench.exe --device 1          :: 选第 1 个设备
vkbench.exe --no-matrix --no-cache   :: 跳过某些分组
vkbench.exe --max-buffer 320    :: 限制工作缓冲（MiB），小显存卡用
vkbench.exe --target-ms 20      :: 每个测点的目标 GPU 时长（默认 15 ms）
vkbench.exe --open              :: 跑完打开 HTML 报告（默认就会打开）
vkbench.exe --no-open           :: 跑完不打开浏览器（脚本/无人值守用）
```

跑之前最好让机器空闲：**测试跑在显示适配器上时，桌面本身也在抢 GPU**，绝对值和离散度都会变差。

| 文件 | 内容 |
|---|---|

| `vkbench-<设备名>.csv` | 逐测点：分组/测点/说明/数值/单位/参数/单次耗时(中位/min/max)/校验结果 |
| `vkbench-<设备名>.html` | 自包含 zh-CN 报告（无外部请求）：顶部大数字概览卡、吸顶导航、算力/带宽条形表、延迟与带宽曲线（缓存层级色带 + 拐点标注 + **鼠标悬停显示数值** + **点图例隐/显曲线**）、矩阵表、可折叠的全部测点表；`@media print` 自动转浅色便于打印。**跑完默认自动用默认浏览器打开**（`--no-open` 关闭） |

默认落在 **exe 所在目录的 `vkbench-report\`**（不是当前目录），`--out` 可覆盖；仓库里有一份[样例报告](sample-report/)（RX 6700 XT 的真实输出）。

## 方法

**设备层。** `vkGetInstanceProcAddr` 动态取 ~55 个入口，不依赖 SDK。特性用 `vkGetPhysicalDeviceFeatures2/Properties2` 探测，按设备 `apiVersion` 选择用核心结构（`Vulkan11/12/13Features`）还是对应的扩展结构，**只启用"已支持且需要"的**特性；设备创建失败会退回"纯核心特性"再试一次，保证在任何设备上都不至于因为多要特性而整个跑不起来。AMD 上额外查 `VK_AMD_shader_core_properties2` 拿 **CU 数**（用它做每-CU 归一和运行时钟推算）。

**计时。** 每个测点用 GPU 时间戳把 dispatch 夹在中间，取 N 次的中位数并记录 min/max；**并且同时记录主机侧墙钟**。这台机器的 AMD 驱动有个实测行为：`COMPUTE_SHADER` 阶段的时间戳在**低占用**时不等计算完成就写（小网格 dispatch 会被严重低估），因此当 GPU 时间戳小于主机墙钟的一半时改用墙钟并给该点打标记。标定逻辑用"GPU 时间戳 + 主机墙钟取保守值"，且单步放大不超过 16 倍、迭代数上限 1e6——一条坏测量不可能让单次 dispatch 变成几分钟。

**算力内核。** 每个算术内核都做两件事：(a) 用 8 个独立累加器保证 ILP；(b) **系数从 push constant 传入四个互不相同的运行期标量**。第 (b) 条是必须的——如果向量是"逐位相同"（splat）的，编译器会把整条向量递推**塌缩成一条标量递推**，实测 FLOPs 会虚高 2~4 倍（这正是第一版报告的 fp32 报出 48 TFLOPS 的原因）。

**正确性校验。** 每个算术内核都在 GPU 上再跑一遍并把结果与 **CPU 参考模型**逐线程对比（fp32 用 `std::fma` 逐通道复刻、整数按位精确）；指针追逐用 CPU 复现整条链；带宽内核校验归约和；矩阵配置用 CPU 矩阵乘法对比。校验不过的测点在报告里直接标 FAIL，不会伪装成有效数据。

**缓存延迟。** Sattolo 单循环置换做指针追逐（保证不可预取），扫 **1 KiB → 1 GiB 的 2 的幂共 21 个点**（默认档；快速档取偶数幂次）。三条曲线：多 CU 聚合（8 链/线程）、单 workgroup（看单 CU 的 L1）、**单 workgroup 单链**（在途请求仅 64 个，排队最小，最接近真延迟）。**缓存层级由延迟台阶推断**：取落差最大的 3 个台阶作为 L1/L2/末级的分界（容量取台阶前一点的容量、延迟取该平台值），再加一条显存行；每级的读带宽用同容量处最近的带宽测点填。若某设备延迟点数不足，回退到用读带宽平台推断。容量始终是**推断值**——Vulkan 没有报告缓存大小的 API。

**带宽。** 读（vec4 归约，内层 4 路展开）/写/拷贝随工作集的大小曲线，另加：
- **访问步长扫描**：每次访问 4 B，步长 4 B→1 KiB，看有效带宽在 32 B / 128 B 处的台阶（sector / cacheline 尺寸）；
- **DMA 拷贝引擎对照**：`vkCmdCopyBuffer`（不走计算着色器），用来给整条计时链条做独立标定。

两条工程细节决定成败：(1) 读内核每轮结束处放一个**数据相关的不可预测早退**，否则编译器把只读 load 提出轮循环，带宽虚高数倍；(2) **网格不能太大**——每个 workgroup 反复读自己那片切片，如果所有常驻 workgroup 的切片合起来能装进末级缓存，重复的轮次根本到不了显存（RX 6700 XT 上实测虚高 3 倍）。所以 >16 MiB 的工作集按"每 workgroup ≥ 8 MiB 切片"给网格，同时保底 32 个 workgroup 以免并行度不足。

**矩阵。** 运行时用 `vkGetPhysicalDeviceCooperativeMatrixPropertiesKHR` 枚举设备声明的配置，与预编译的 12 个变体表匹配后实测；设备声明但没预编译的配置会在报告里列出。每个配置额外跑一次小子集并与 CPU 矩阵乘法对比。

## 这台机器的结果（RX 6700 XT，Adrenalin 26.8.1，amdvlk 1.4.315）

与公开规格对表（括号里是规格值）：

| 项目 | 实测 | 规格 / 推算 |
|---|---|---|
| FP32 FMA (vec4) | 12.2~13.1 TFLOPS | 13.21 TFLOPS（40 CU × 128 flops/cycle × 2.58 GHz） |
| FP16 打包 | 25.4~26.0 TFLOPS | ≈ 2× fp32（RDNA2 打包半精度） |
| FP64 | 801~826 GFLOPS | 1/16 × fp32 = 825.6 ✓ |
| INT8 DP4A | 24.6~25.7 TMAC/s | 25.6（40 CU × 64 通道 × 4 MAC × 2.58 GHz） |
| SFU | 1.59~1.68 T ops/s | ≈ 1.6 |
| 共享内存 LDS 读 | 7.9~8.1 TB/s | 128 B/cycle/CU 上界 12.8 |
| 显存 读/写/拷贝 | 311~372 / 265~338 / 242~321 GB/s | 384 GB/s（192-bit × 16 Gbps） |
| DMA 拷贝引擎对照 | 313~318 GB/s（R+W 计） | — |
| 缓存延迟（1 KiB→1 GiB 扫频） | L1 ≤16 KiB **41.5 ns**；L2 ≤2 MiB **124 ns**；末级/IC ≤64 MiB **228 ns**；显存 ≥128 MiB **462 ns** | L2 3 MiB、Infinity Cache 96 MiB（台阶落在量级正确的位置） |
| 各级读带宽 | L1 级 547 GB/s（单 CU 视角）· L2 级 2197 GB/s · 末级 1224 GB/s · 显存 377 GB/s | 末级/显存 = 3.3 倍 |
| 推算运行时钟 | 2.29~2.56 GHz | boost 2.58 GHz |

架构画像里几条一眼能看出性格的：

- **ADD 是 FMA 的 ~2 倍**（24.1~26.1 vs 12.2~13.1 TFLOPS）→ 加法走第二条发射路径，FMA 才是单发射上界；
- **vec4 与标量速率相同** → 指令逐线程标量执行，向量宽度不改吞吐；
- **SFU:ALU ≈ 1:7.8**、**IMAD:FP32 ≈ 1:4**、**LDS:显存 ≈ 21:1**；
- **512~1024 个 workgroup 达到 95% 峰值**（4096 个 group 时因桌面干扰离散度变大）。

矩阵（cooperative matrix）在这台机器上**数据本身不稳定**：f16→f32 的配置在不同轮次给出 12.97 / 8.37 / 3.82×fp32 等互相矛盾的值，超过本机 fp16 ALU 上界的点会被报告自动剔除并注明。合理解释是 RDNA2 没有独立的 WMMA 硬件，驱动用 ALU 模拟，代价抖动很大——**这条本身就说明"没有独立矩阵单元"**，但具体倍率不可信，报告里已标注。

## 踩过的坑

每一条都曾经让报告数字错得离谱，且都在这台机器上实测复现过：

1. **逐位相同的向量被编译器塌缩成标量。** 第一版 fp32 内核里 `b/c` 是 splat 向量（四个通道一样），LLVM 能证明整条 `a = fma(a,b,c)` 递推保持 splat，于是 vec4 版本只按 **1 个通道** 执行——实测 FLOPs 恰好是 vec1 的 4.0 倍、vec2 的 2.0 倍。修法：系数改成 push constant 里的 4 个互异标量。修完 vec4 ≈ vec1 ≈ 13 TFLOPS，与规格一致。
2. **整数加法可以直接被合并。** `a = a + c` 重复 32 次是合法可重组为 `a + 32c` 的（整数加法满足结合律），IADD 内核因此测到 100+ TOPS 的假值。结论：**不要单独测整数加法**，本工具已删掉该测项。
3. **只读循环被提出轮循环。** `for r { for i { acc += a[i] } }` 里内层 load 与外层轮次无关，编译器把后几轮免费了——192 MiB 工作集读出 1174 GB/s（本卡上限 384）。修法：每轮结束放一个"数据相关且永不成立"的早退分支。
4. **网格切片恰好落进末级缓存。** grid-stride 循环里每个 workgroup 反复读自己那 184 KiB 切片，40 个 CU 的常驻切片合计 ~59 MiB < 96 MiB Infinity Cache → 测到的是**末级缓存带宽**而不是显存带宽（虚高 3 倍）。修法：大工作集按"每 workgroup ≥8 MiB"给网格。
5. **AMD 驱动的 `COMPUTE_SHADER` 时间戳在低占用时不等计算完成。** 1 个 workgroup、262144 次迭代的 dispatch 报 6 µs（真值几十毫秒）。表现是占用扫描曲线非单调（1:273702, 2:243653, 16:43733 …）。修法：同时测主机墙钟，时间戳小于墙钟一半就改用墙钟并打标记。
6. **管线是惰性编译的。** 新建管线的**首次** dispatch 明显更慢，标定会把迭代数压小；现在每次建完管线先空跑一次再计时。
7. **uint32 输出被当 float 读回。** 校验里 `(uint32_t)got[i]`（got 是 float 数组）会把位模式 `0x84445C4F` 解释成一个极小的非规格化数，转回来是 0——导致 5 个整数内核"校验失败"（假失败）。改成按原始 32 位读回。
8. **驱动可能走 24 位乘法路径。** IMAD 的乘数小于 2^24 时驱动可以用 `V_MAD_U32_U24`（把操作数截断到 24 位），与 32 位参考模型不符；内核系数改成 >2^24 强制全宽路径后校验通过。
9. **小程序员的"顺手取值"会毁掉标定。** 标定最初只用 GPU 时间戳：某次测量被低估 30 倍 → 迭代数被放大到 4e9 → 单次 dispatch 变成几分钟（进程烧了 8 分钟 CPU 时间）。现在每步放大不超过 16 倍、迭代上限 1e6，并用墙钟做失控保护。
10. **中文/编码。** C++ 源码用 `/utf-8` 编译、控制台 `SetConsoleOutputCP(CP_UTF8)`；构建脚本（.ps1/.bat）保持纯 ASCII——Windows PowerShell 5.1 会把无 BOM 的 UTF-8 脚本按 ANSI 读。
11. **报告里的曲线画在了 NaN 坐标上。** 我先把数据点从数组 `[x,y]` 改成对象 `{x,y}`，但 `chart()` 内部还在读 `p[0]/p[1]`——浏览器里曲线整条消失，而"画了几条线"的计数完全正常。修法：统一用 `p.x/p.y`，并给校验脚本加**非有限坐标断言**（`nan=0`），这类错误以后会在构建时就暴露。顺带一提，校验脚本现在还会真的触发一次悬停与图例点击，走通交互分支。
12. **层级推断的填充顺序。** 每级"读带宽"最初在延迟推断*之前*填充，而延迟推断会重建整个层级表——于是带宽列全是 0。改成延迟推理之后按容量最近点填。另外真实层级常有 4 个台阶（本机就是），只取前 3 个会把"末级缓存"错标成显存，所以改成**按落差大小取前 3 个台阶**（L1/L2/末级通常 1.5-1.8 倍，分区/相联度造成的伪台阶接近 1.3 倍）。
13. **重建时 exe 被占用。** 基准还在跑的时候调 build.bat 会 `LNK1104: 无法打开 vkbench.exe`，构建失败但脚本继续，于是用旧 exe 跑出了旧报告。先确认没有 vkbench 在跑再构建。
14. **本机 PATH 里有个拼写错误**（`C:\indows\system32`），System32 不在 PATH，所以 `build.bat` 开头先把 `%SystemRoot%\System32` 和 Node 目录补回 PATH；所有系统工具（curl/tar/tasklist）用全路径调用。

## 局限

- **缓存容量是推断值**，不是 API 报告值；末级缓存与显存的分界受命中率曲线形状影响，报告里给了原始曲线可自行判读。
- 显示适配器上的测量会被桌面抢占，**离散度**会体现出来（报告里逐点记录）；要更干净的数字，跑之前让桌面空闲。
- 矩阵分组在本机（RDNA2 + amdvlk）数值不稳，已按物理上界过滤 + 标注；换到有独立矩阵硬件的卡上应可直接读到有用的倍率。
- 单次 dispatch 目标 15 ms、迭代上限 1e6，是为"几十秒出报告"设计的；要极致精度就 `--full --target-ms 40`。
